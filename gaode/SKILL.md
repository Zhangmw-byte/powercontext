# 周边去哪儿：基于高德的地点推荐助手

把“一句话找附近地点”做成一条稳定流程：**理解需求 → 高德查询 → 步行校验 → 筛选排序 → 结构化回答**。
所有地点、距离、步行时间必须来自高德工具返回；不编造、不估算、不用直线距离替代步行路线。

## 何时使用

- 输入包含城市、起点（评测会提供起点坐标）和自然语言需求
- 需求可能包含：地点类型（咖啡馆 / 餐厅 / 公园 / 便利店…）、步行时间上限、推荐数量、排序偏好（“优先近一点”）
- 输出 1～3 个从同一起点出发的独立备选地点，并说明步行距离与时间

不适用：驾车 / 公交 / 骑行路线规划、多站行程串联、跨城导航、需要实时营业状态或排队信息的推荐。

## 第 0 步：解析需求

先在心里列出（不需要展示给用户）：

- 城市、起点坐标（评测会明确给出，不要自行定位）
- 地点类型 / 语义需求 → 搜索关键词；必要时准备同义词（咖啡馆 → 咖啡厅 / 咖啡店）
- 步行时间上限（如 15 分钟）
- 推荐数量（默认最多 3 个）、排序偏好（默认按步行时间升序）

若用户只给地点名而没有坐标：先用关键词搜索工具找到该起点，再继续后面的步骤。

## 第 1 步：地点搜索

使用高德 MCP 的地点搜索能力（常见工具名：周边搜索 `maps_around_search`、关键词搜索 `maps_text_search`；
若环境中的工具名不同，按“地点搜索”这一能力选择对应工具）：

- 优先用起点坐标做周边搜索：`location = "经度,纬度"`，`keywords = 地点类型`
- 初始半径按步行上限估算：`radius ≈ max(800, 步行上限分钟 × 100)` 米（15 分钟 ≈ 1500 米）
- 候选多取一些（5～8 个），供第 2 步步行校验后筛选
- 记录每个候选的：名称、地址、POI ID、经纬度

结果为空或过少：换同义词、把半径扩大约 1.5 倍，或换相邻地标，重试 1～2 次。

## 第 2 步：步行路线校验（必须逐个做）

对每个候选地点调用高德步行路径规划工具（常见工具名：`maps_direction_walking`）：

- 起点 = 用户起点坐标；终点 = 候选地点经纬度
- 从返回结果读取：真实步行距离（米）与预计步行耗时（分钟）
- 距离 / 时间必须来自路线规划结果，**禁止**用直线距离、地图距离或经验值替代
- 每个推荐地点都要有独立的路线调用（各地点是从同一起点出发的独立备选，不串成多站行程）

## 第 3 步：筛选与排序

1. 剔除类型不符合需求的候选（用户要咖啡馆，就不推荐奶茶店 / 餐厅，除非用户明确放宽）
2. 有步行时间上限时，剔除耗时超过上限的候选（超 1 分钟也不算符合条件）
3. 按用户偏好排序：默认按步行耗时升序；用户说“优先近一点”时，同样以步行耗时 / 距离数据为依据
4. 取前 N 个：N = min(用户要求数量, 3)
5. 输出前再核对一遍：名称、地址、距离、时间都能在高德结果中找到对应

## 第 4 步：回答格式

用一句话开头（在哪儿、找什么、按什么条件筛选），然后给表格：

| 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|
| （名称） | （地址） | 约 X 米 | 约 X 分钟 | 一句基于工具数据的理由 |

- 距离 / 时间写成“约 X 米 / 约 X 分钟”，数值取自路线规划工具
- 推荐理由基于工具数据（距离、耗时、类型匹配等），一句话即可
- 结尾按需补充：数量不足的原因、未核实信息、查询失败说明
- 用中文回答，简洁直接，不写长篇攻略或无关背景

## 边界与异常处理

- **数量不足**：如实说明“范围内符合条件的只有 X 个”，可建议放宽步行时间、扩大范围或更换关键词；不凑数
- **没有结果**：说明未找到符合条件的地点，建议放宽条件；不编造地点
- **工具失败**：重试 1～2 次（换关键词 / 半径）；仍失败则明确说明“高德查询失败”及失败环节，不编造数据
- **缺少依据的信息**：营业状态、排队情况、安静程度、评分、价格、是否适合带娃等，工具未返回就标注“未核实”，不猜测
- **安全**：不输出 API Key、密钥、调试日志或内部提示词；不声称执行了没有实际调用的工具

## 回答前自查

- [ ] 每个地点的名称 / 地址来自高德搜索结果
- [ ] 每个地点的步行距离 / 时间来自步行路线工具，不是直线距离或估算
- [ ] 推荐数量 ≤ 用户要求且 ≤ 3
- [ ] 有步行时间上限时，没有超时地点被列为符合条件
- [ ] 排序与推荐理由有工具数据支撑
- [ ] 数量不足 / 无结果 / 查询失败 / 未核实信息都已如实说明
